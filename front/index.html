Trabajo en Pareja

Cómo nos organizamos para trabajar

Estrategia de desarrollo paralelo sin bloqueos, aplicando buenas prácticas de Git colaborativo y arquitectura por capas.

División de Capas sin Bloqueos

Para no pisarnos ni esperar por dependencias técnicas, dividimos el proyecto por áreas claras:

  • Lado A: Dominio, Value Objects, Servicios, interfaz interactiva CLI y repositorios provisionales InRam.
  • Lado B: Persistencia relacional, DAOs con JDBC, Dockerfile Multi-stage y Docker Compose con MySQL.

Flujo Git Limpio & Rebase

Control exhaustivo del historial de Git para evitar "commits de merge" sucios y conflictos imprevistos:

  • Ramas de feature atómicas (Feature/evente-domain, chore/docker).
  • Actualización con git fetch + git rebase dev para mantener un árbol lineal.
  • Uso seguro de --force-with-lease para sincronizar ramas rebasadas sin destruir trabajo ajeno.

Definición y Validación

Nada se implementó a ciegas. Cada paso siguió un protocolo de verificación consensuado:

  • User Stories con Checklist: Criterios de aceptación detallados antes de escribir código.
  • Pull Requests con Markdown: Desglose minucioso de cada PR para facilitar la revisión del compañero.
  • Batería de Pruebas Cruzadas: Validación interactiva tanto en memoria como en MySQL dentro de Docker.
Criterio Técnico

Decisiones de Diseño Destacadas

En software no hay soluciones mágicas, sino balances de compromiso (*trade-offs*). Estas son las decisiones arquitectónicas clave y el porqué detrás de cada una.

01 • Dominio / DDD

Value Objects vs Primitive Obsession

Descartamos usar String o LocalDate desnudos. Creamos Java Records (TaskTitle, EventCelebDate) que se auto-validan en su constructor factoría.

✔ Regla: EventCelebDate no admite fechas anteriores al 01/01/2000 (previene erratas tipográficas).
02 • Patrones / Pragmatismo

Descarte de Observer (KISS / YAGNI)

Evaluamos usar el patrón Observer para avisos de eventos. Lo descartamos: en una CLI síncrona bloqueada por Scanner, notificaciones asíncronas corrompen la vista interactiva.

✔ Consulta directa: listUpcomingEvents() con refresco automático de recurrencias.
03 • Persistencia / BD

ON DELETE CASCADE en MySQL

Inicialmente coordinábamos la eliminación de notas y tareas desde la CLI. Al pasar a MySQL, delegamos el borrado en cascada a las claves foráneas del motor relacional.

✔ Desacoplamiento: TaskCli solo necesita conocer a su propio TaskService.
04 • Arquitectura de Datos

Identidad UUID y Método restore()

Las entidades nacen con su UUID en Java sin esperar al ID de BD. Creamos métodos separados: create() genera nueva identidad y restore() reconstruye fielmente desde persistencia.

💡 Reflexión: UUIDv7 habría ahorrado el campo createdAt y optimizado los índices B-Tree.
05 • Evolución Arquitectónica

Repositorio InRam → Futura Caché

La interfaz Repository permitió reemplazar memoria por MySQL sin alterar una sola línea de lógica de negocio. Decidimos conservar InRamRepository para reutilizarlo como caché.

✔ Seguridad: InRam usa copias defensivas con restore() protegiendo la mutabilidad.
06 • Rendimiento & Red

Singleton en ConnectionFactory

Reutilizamos una única conexión TCP compartida para todos los DAOs, descartando abrir sockets en cada consulta. Validamos salud con isValid(2) y cerramos en el finally de Main.

✔ Ahorro: Se elimina la latencia de apretones de manos TLS/TCP en cada listado.
